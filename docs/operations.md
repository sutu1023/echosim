# M0 操作与验证

## 工程基线

依赖、镜像准备后标准测试不访问公网：`make prepare` → `make test`。每次源文件变化需要重新prepare；源码指纹防止测到旧镜像。`make check` 自动重新准备并执行完整门禁，需要网络更新漏洞数据。测试使用随机Compose项目名、独立数据库、内部网络；退出时仅清理测试容器和测试卷。

运行栈为 echosim_m0，默认仅127.0.0.1:18380。已有其他项目或端口不属于本脚本清理范围。`make down`保留开发数据库卷；不要随意使用down -v。API应用日志使用UTC日分文件，保留最多7个UTC日期并限制总大小50MiB，每分钟与启动时清理。运行栈不持久化容器stdout，避免另一份不受期限控制的日志；make logs读取应用JSON文件。代理错误日志删除request对象并固定消息。M4再启用完整指标告警。

## 本地回退与恢复

make test在独立测试栈验证 candidate-v2 → test-v1版本切换，并发送真实停止信号记录时间。额外在独立数据库插入合成记录，pg_dump后用Node内置AES-256-GCM认证加密，验证篡改会失败，再恢复到第二个数据库核对记录并清理。密钥仅管道内存、没有凭证或明文数据库备份进入报告。

这些是本地合成演练，不是公网蓝绿、异地备份、RPO/RTO生产达标证明。M4必须在获批服务器/域名/备份位置实测；预算账本恢复后核对供应商用量，删除清单不可随旧库回滚，确认前不开放服务。

## 机密事故

维护者先停用/轮换泄露凭证，再清工作区及提交历史，重扫并记录处置。删除文件不能代替轮换。不要将Key粘贴进issue或截图。仓库钩子扫描暂存区；CI扫非忽略工作区和全部提交历史，真实.env若误跟踪也不得豁免。

## 发布策略

常规PR Squash，门禁与独立审查通过可自动合并。正式公网发布、预算增加、新安全例外和破坏数据操作由维护者决定。未来生产蓝绿须共享并发预算，并用运行者心跳区分任务；当前M0未实现业务调度，不声称已支持蓝绿任务交接。
