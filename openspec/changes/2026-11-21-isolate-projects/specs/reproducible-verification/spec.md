# Spec Delta

## ADDED Requirements

### Requirement: 隔离用户路径可重复验收

`make verify` SHALL 在同一个被测 SHA 上回放账户隔离用户路径，并保证重复执行不因账号或项目残留而失败；准备账号与清理数据 MUST 使用幂等操作，不得要求人工介入。

#### Scenario: 重复执行隔离场景

- **WHEN** 在已存在验收账号与验收项目的环境中再次执行 `make verify`
- **THEN** 命令以退出码 0 结束，不因邮箱重复或项目重名而失败
- **AND** 每次执行都使用可区分的新项目名称，报告记录本次创建的项目标识

#### Scenario: 账号准备失败时明确失败

- **WHEN** 用于验收的两个账号无法创建或更新
- **THEN** 验收以非零退出码结束，并以独立场景记录失败原因
- **AND** 不把后续接口检查记为通过

## MODIFIED Requirements

### Requirement: 验收覆盖关键可观察场景

一次成功的验收 SHALL 实际验证启动、健康检查故障与恢复、后端进程不重启、以及账户隔离用户路径等场景，而不是只做静态检查。

#### Scenario: 报告包含全部验收场景

- **WHEN** `make verify` 成功结束
- **THEN** 报告逐项记录并通过：首页可访问并包含 EchoSim、`/health` 返回 200、停止数据库后返回 503、恢复数据库后返回 200、后端进程标识在故障前后不变、账户隔离用户路径通过、连续执行可重复
- **AND** 停止数据库到返回 503 的实测耗时被记录且不超过 5 秒

#### Scenario: 隔离用户路径逐步通过

- **WHEN** 验收使用两个真实账号 A 与 B 回放隔离路径
- **THEN** 报告至少包含以下可观察结果：A 登录成功、A 创建项目后刷新列表仍可见且详情返回 200、A 退出后旧会话访问私有接口返回 401、B 的列表与历史均不含 A 的项目、B 访问 A 的项目 ID 与访问不存在 ID 的状态码和响应体相同、A 重新登录后仍能打开原项目
- **AND** 每个结果作为独立场景记录在报告中

#### Scenario: 关闭重开浏览器后的会话被验证

- **WHEN** 验收在会话有效期内用仅携带原 Cookie 的新客户端请求会话查询与项目详情
- **THEN** 两者都返回 200 与同一用户数据，证明会话不依赖浏览器进程内存
- **AND** 该结果作为独立场景记录在报告中
