# Design

## Context

本变更针对武大项目已上传的 25 页报告、同一个建图问题与旧 build `f4c9a593-aa36-49e3-84cf-125ccaa88c21`。旧图与当前 Change 08 路径都已暴露同一问题：模型先产出 JSON 抽取清单，worker 再把清单当 episode 写入，读回后只发布命中清单的关系；主体白名单、清单键和批次内局部名称共同限制了最终图。

EchoSim 已有可复用的底座：材料入库已清理 PDF 页眉页脚并保存页码/UTF-16 区间；六步建图、租约、幂等 episode、按 episode UUID 读回、部分/最终快照原子发布、来源定位与工作台跳转均已存在。本变更复用这些约束，替换“规划主体白名单 + 抽取清单”主链路。

## Goals / Non-Goals

**Goals:**

- 从现有材料重建建图全文，保留段落、标题、跨页衔接，按 500/50 分块并保留原始页码与字符区间。
- 模型基于整份报告与问题规划实体/关系类型，不再限制首轮登记主体数量。
- 使用参考项目主链路：设置本体 → 原文分块作为 episode → 等待索引 → 按 build 分页读回全部节点/边/事实。
- 读回事实可关联 episode、定位支持原句并映射回材料坐标；保留来源性质四项区分与两条回归。
- 新 build 独立图谱，旧 build 可读；用真实 25 页报告跑出新图并交付实际计数与可核对关系。

**Non-Goals:**

- 不把模型二次抽取的 JSON 作为发布事实来源。
- 不新增模型实体消歧调用、图算法或手工补图界面。
- 不以 Node/Edge 数量、画布密度或截图观感作为通过条件。
- 不改变 Change 07 的六步、租约、事件、快照可见性与原文坐标语义。
- 不扩大私有材料授权范围，不让默认命令或 CI 触发真实外呼。

## Decisions

### 1. 建图全文复用已入库分块，跨页重建后按 500/50 切分

**决定**：建图步骤从 `document_chunks` 读取已清理的材料分块，按 chunk 顺序重建每个文档的建图全文：

- 同一页内存在重叠时，按 `source_start`/`source_end` 的 UTF-16 区间裁掉重复前缀；
- 不同物理页之间插入段落分隔，保留跨页衔接；
- 标题、正文行与段落换行保持入库清洗后的形式，不再重新拼接全文后推算页码；
- 对重建全文按 500 字目标、50 字重叠切分，优先句末，其次空白，单句过长才硬切。

每个建图分块保存 `text` 与逐字符映射：物理页码、材料内 UTF-16 偏移、来源 `documentChunks` 序号、段落区间。映射与分块文本共同写入建图步骤载荷，作为读回后来源定位的唯一坐标依据。旧材料不需要重新上传，也不改写 `document_chunks`。

**理由**：入库阶段已经完成页眉页脚清理、页码绑定与 UTF-16 坐标记录；直接复用可保证“工作台点回原文”与既有材料坐标一致。重建全文解决跨页衔接，500/50 与参考项目一致，且 25 页报告体量足以一次放入模型上下文。

**备选方案**：重新解析 PDF 再切分（否决：可能改变已入库坐标，旧材料需重传）；直接使用现有 1200/120 分块（否决：与参考项目链路不一致，单块过大不利于按事件抽取）；只按页面切分（否决：丢失跨页上下文）。

### 2. 规划阶段只设计类型，不登记主体白名单

**决定**：模型只输出 `entityTypes` 与 `relationTypes`：

- 实体类型覆盖报告中的机构、部门、当事方、群体、事件、决定/安排、媒体/平台等，要求可识别、可区分，拒绝“实体/细节/关系”等占位名；
- 关系类型使用原文动作词（如“发布”“执行”“回应”“报道”“维权”），拒绝“关联/相关/提及”等泛化词；
- 类型数量以覆盖报告为准，不设置“首轮最多 N 个主体”的注册表，也不要求后续抽取围着固定名单；
- 服务端校验类型名、关系端点类型和规模，不要求模型输出批次或主体依据。

**理由**：参考项目的本体只负责类型边界，实体实例由图谱服务从原文抽取。主体白名单会把“报告后半段才出现的主体”永久排除，也是当前图变小的直接原因。类型规划一次看到全文与问题即可完成，不需要按批次二次抽取。

**备选方案**：保留主体注册表但不限制数量（否决：仍会迫使模型先列名单，遗漏未列入主体）；完全不让模型规划本体（否决：图谱服务需要类型提示；没有本体时关系类型容易退化为通用标签）。

### 3. 主链路改为“原文 episode → 索引 → 按 build 读回”

**决定**：六步保持 `bind/plan/extract/write/readback/publish`，职责调整为：

1. `bind`：为本次 build 准备独立图谱；真实 provider 新建 build 图谱，不复用旧 build 的图谱。
2. `plan`：模型基于整份报告与问题输出实体/关系类型并持久化。
3. `extract`：从材料重建建图全文并按 500/50 切分，保存分块与逐字符映射；把本体设置到本次 build 的图谱。该步不再调用模型抽取。
4. `write`：把每个原文分块的纯文本作为 episode 写入，episode 元数据保留 buildId 与 chunk 键；沿用幂等键、响应丢失检索确认与旧令牌拒绝。
5. `readback`：按本次 build 的 episode UUID 分页读回节点、边与事实；已处理 episode 批次稳定后立即发布部分快照，不等待全部完成。
6. `publish`：最终快照、`ready`、`canContinue`、完成事件与任务成功同一事务。

读回不要求命中旧抽取清单。发布范围由本次 build 的 episode UUID 决定，服务端返回的旧 build/旧图谱对象不会进入快照。

**理由**：这是参考项目已验证的主链路，能让每个原文分块都贡献图谱服务实际识别出的机构、当事方、事件和行动。保留六步是为了不改变既有租约、事件、快照与验收约束。

**备选方案**：继续写 JSON 抽取清单（否决：当前问题根因）；读回全图后不按 episode 过滤（否决：混入旧 build 数据）；每个分块单独建图（否决：无法形成整图且成本高）。

### 4. 读回节点归并、边去重与 build 隔离

**决定**：

- 只接受 episode UUID 与本次 build 有交集的节点/边；没有 episode 归属的对象不发布。
- 节点按 NFKC 规范化后的名称归并；同一名称跨页/跨 episode 只保留一个快照节点，合并其材料来源与参与关系。不同名称保持不同节点。
- 边先解析两端到归并后的节点，再按起点、终点、关系类型与规范化事实去重；同一事实重复读回只保留一条边并合并来源。自环边不发布。
- 关系类型优先映射回本次本体规划中的动作名称；映射不到时保留服务端关系名，但必须有支持原句。
- 新 build 使用独立图谱；旧 build 的图谱、快照与来源保持不变。

**理由**：真实服务会返回同一主体的多个节点、同一事实的多条重复边；如果不归并，画布会被重复项淹没，跨页主体也难以从一个节点查看。按名称归并是确定性规则，不需要额外模型调用；独立图谱从源头避免旧 build 数据混入。

**备选方案**：完全依赖服务端实体消歧（否决：仍会返回重复节点/边）；按 UUID 去重（否决：同一主体仍有多个 UUID）；合并所有同名节点但保留旧图谱（否决：旧 episode 关联可能污染新图）。

### 5. 读回事实 → episode → 支持原句 → 原文坐标

**决定**：

- 每条读回边先取其 episode UUID 集合中属于本次 build 的 episode，再在这些原文分块中寻找支持句。
- 支持句优先单句；允许使用相邻句、明确指代和有依据的简称补齐主体/对象。候选句按与事实描述的字面重合、端点名称出现、动作词出现综合排序。
- 每条发布关系必须有同时支持起点、动作与对象的原句；只有媒体名单、机构名单或实体名称而无动作的句子不能作为关系来源。
- 关系的 `claimNature` 由支持句、动作与起点类型确定：明确转述或媒体来源为 `media_report`；当事方指控/回应/维权等为 `party_claim`；作者/报告提出的应做事项为 `author_recommendation`；只有原文明确出现决策主体与已作出动作（决定/作出/发布/判决/处分等）才为 `official_decision`；其余为 `other_material`。
- 平台类型节点作为起点、群体/个人类型节点作为终点且动作是用户行动时，最终边改为“用户 → 平台”并标记 `platform_action`；界面读成“用户在平台上行动”，不再画成“平台向用户行动”。
- 支持句出现“不实信息/谣言/传闻/据称/被指/所谓”等限定且被限定对象就在附近时，目标节点派生为“待核实说法”，边标记 `attributed_claim`；不把被转述的说法单独画成已发生事件。
- 建议/呼吁/撤销/纠正等表达必须保留为建议或当事方主张，不能挂成已经发生的正式决定。正式决定句需要出现决定主体、动作与对象，且不能被“建议/呼吁/应”前置修饰。
- 节点来源取该节点在某 episode 中可定位的名称/身份原句，最多 5 条；关系来源按关系分别保留，最多 5 条。来源坐标由建图分块的逐字符映射生成。

**理由**：参考项目只返回事实与 episode，不保证每条边都能直接对应一句原文；必须在 EchoSim 侧补上“证据可点回原文”。这两条回归直接对应用户最容易误读的媒体名单与建议撤销。

**备选方案**：直接使用服务端事实作为引文（否决：事实是生成句，不能定位原文）；只接受与事实逐字相同的句子（否决：服务端会改写动作与名称，召回过低）；把建议一律丢弃（否决：会丢失报告作者的重要观点）。

### 6. 快照、接口与工作台

**决定**：

- 快照节点保存归并后的名称、语义类型与代表性来源；边保存起点、终点、动作类型、动作标签、事实摘要与 `claimNature`。
- 接口沿用现有快照结构，节点/边来源继续使用 `locator` 跳转 PDF 页码或文本区间。
- 工作台节点显示完整名称；节点详情列出参与关系及页码；关系详情显示“起点—动作—终点”、来源性质、事实描述和支持原句。
- `media_report`、`party_claim`、`official_decision`、`other_material` 分别显示为媒体报道、当事方主张、机构正式决定、其他材料陈述；旧快照空性质不默认成正式决定。

**理由**：现有快照接口已支持来源定位与 build 守卫，不需要新增端点；把新语义写入快照后，页面不需要推断。

**备选方案**：前端直接调用图谱服务（否决：绕过鉴权、项目归属与快照隔离）；把事实和性质塞进 `summary`（否决：无法稳定显示与校验）。

### 7. 真实 25 页验收以实际计数与可核对关系为准

**决定**：

- 在武大工作台用同一份 25 页报告、同一问题新建 build，执行全新的本体规划、全文写入、索引、读回与发布。
- 交付时记录并核对：覆盖页数、写入原文块数、图谱服务读回节点/边数、最终发布节点/边数。
- 若读回计数远高于最终发布计数，必须定位损失发生在节点归并、边去重、支持句定位还是快照上限，并修复后再交付。
- 人工抽查至少三条分布在不同事件和页码的关系，确认能点回支持原句。
- 旧 build 仅供对照，不被覆盖；校园夹具只做回归，不进入真实图结论。

**理由**：用户要判断整张图质量，必须看到真实链路各阶段的数字与抽样关系，而不是只看最终节点数。计数差异是定位“读回丰富但展示很少”的直接诊断信号。

## Risks / Trade-offs

- **500 字分块仍可能切散跨句事件** → 50 字重叠与相邻句支持缓解；来源定位允许相邻句，但发布关系仍要求主体、动作、对象。
- **真实服务返回大量重复节点/边** → 确定性名称归并与事实去重；若归并后仍超过 500/800 上限，按既有规则明确失败，不截断。
- **服务端事实与原文措辞差异大** → 候选句按字面、端点和动作综合排序；找不到支持句的关系不发布，并在诊断中记录丢弃数量。
- **媒体名单/建议撤销误判** → 两条回归覆盖；来源性质采用保守规则，正式决定被转述时降级为报道/主张。
- **独立图谱成本增加** → 仅在真实建图时创建；默认命令、CI 与替身路径不触发。
- **旧 build 兼容** → 新字段可空，旧快照按空性质读取；旧图谱与快照不删除、不回填。
- **私有材料外发** → 只沿用现有授权；未授权时不发起真实 build，验收标记阻塞。

## Migration Plan

1. 保留 `0009` 迁移与旧 build 数据；新链路不需要新增表，建图全文分块映射进入建图步骤载荷。
2. 部署本体规划、建图全文、原文 episode 写入、读回归并与快照物化代码；旧 build 继续可读。
3. 运行单元测试、前端测试与默认 `make verify`，确认离线路径零真实外呼。
4. 在武大工作台对 25 页报告执行真实新 build，记录各阶段计数并抽查关系来源。
5. 人工确认三点后写入 `docs/acceptance/`；签收前不归档。

## Open Questions

无。真实服务在武大报告上的抽取质量由本次新图与计数回答；实现不在验收前放宽支持句或来源性质标准。
